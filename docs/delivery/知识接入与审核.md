# 知识接入与人工审核：本地闭环

这批功能解决的是：**用户整理的业务知识，如何经过检查和人工确认后，真正被查询专家召回。**

范围是原文知识接入链的本地实现。没有连接淘宝内网 TisPlus、DataWorks，也不是自动抓取文件、自动发现口径或企业双人审批。不要把这些外部能力标为已接通。

## 1. 先理解几个词

- `Knowledge`：知识，例如“GMV 只统计已支付订单”。它不是订单原始数据。
- `Draft`：草稿。保存在独立表中，Agent 看不到。
- `Publish`：发布。显式人工确认后，写入可检索的知识表。
- `Reject`：拒绝。本次草稿不能进入知识检索。
- `Owner`：所有者，来自当前登录账号，而不是网页自己传入的用户名。
- `CAS`：Compare And Set，先比较版本，再更新；防止旧页面覆盖新修改。
- `Audit`：审计，保存谁在什么时候做了什么，以及当时的内容快照。
- `AST`：抽象语法树，把 SQL 当语法结构分析，不是把它执行一遍。

## 2. 实际完成了什么

支持四类人工知识：

1. `L1_MODEL`：数据模型说明。例如数据表有哪些字段、数据粒度是什么。
2. `L2_SQL`：查询说明或 SQL 示例。可附带只读 SQL 片段。
3. `L3_RULE`：业务口径。例如订单数如何统计。
4. `L4_LINEAGE`：字段血缘说明。例如汇总金额来自哪些字段。

指标代码必须在 `metric_definition` 注册，或者使用 `*` 表示通用知识。不是输入一个未知指标名，就会自动产生真实指标。

知识正文最多 6000 个字符，标题最多 256 个字符，可选 SQL 最多 16000 个字符，审核备注最多 1000 个字符。未注册指标、空白正文、明显误粘的密钥、SQL 超出受控表字段范围等，都会被拒绝。

**自动检查只证明格式和技术边界通过，不证明业务描述正确。** 发布仍要求人工确认，并填写检查依据。

## 3. 一份知识的生命周期

```text
录入内容 → 校验字段、指标、可选 SQL → DRAFT 草稿
                                      ├─ 人工确认发布 → PUBLISHED
                                      └─ 人工确认拒绝 → REJECTED

PUBLISHED → 创建新版本草稿 → 修改 → 再次人工确认 → 新的 PUBLISHED
```

已发布和已拒绝的草稿均不可直接修改。被拒绝后，可把修订后的内容重新录入为新草稿。

新版本草稿不会影响当前已发布版本。新版本确认发布后，才把旧知识的 `active`（是否参与检索）改为 `false`。旧正文、版本、审核记录保留，不覆盖、不删除。

两个新草稿同时尝试替换同一旧版本时，只有一个能成功；另一个得到版本冲突，仍保持草稿状态。

## 4. 从网页到 Agent，代码怎样串起来

网页的“知识草稿与人工发布”区域可创建、编辑、发布、驳回、修订和查看审核记录。打开该区域后，页面只读取当前登录账号的草稿；发布按钮需要审核备注和明确勾选确认。网页源码位于 `ecom-agent-bootstrap/src/main/resources/static/index.html` 和 `app.js`。

接着看接口：

`ecom-agent-api/src/main/java/com/ecom/api/KnowledgePublishingController.java`

它读取登录用户 `Principal`（当前身份），再把创建、编辑、发布等请求交给领域接口。沿用现有 `/api/**` 安全规则：登录角色必须是 `ANALYST`，写操作必须带 CSRF 令牌。

再看数据契约：

`ecom-agent-domain/src/main/java/com/ecom/domain/KnowledgePublishing.java`

里面的 `Content`、`Draft`、`Review` 等 `record` 是请求和响应的数据结构；`Service` 声明业务能力，不直接操作数据库。

接着看实现：

`ecom-agent-infrastructure/src/main/java/com/ecom/infrastructure/JdbcKnowledgePublishing.java`

这里是真正的业务处理：

1. 检查 `owner`，读取本人草稿。
2. 检查正文长度、已注册指标、审核确认和版本号。
3. 如果填写 SQL，调用 `Lineage.Service.analyze()`。
4. 使用带 `owner + id + status + version` 条件的更新语句，实现乐观锁。
5. 发布时写入 `knowledge_document`，同时保存审计快照。
6. 整个发布过程放在一个事务中；中途失败，草稿状态、旧版退役和新知识写入一起回滚。

SQL 检查继续进入现有文件：

- `ecom-agent-infrastructure/src/main/java/com/ecom/infrastructure/JdbcLineageService.java`：从服务端白名单和数据库实际字段获得受控 Schema（表结构）。
- `ecom-agent-tools/src/main/java/com/ecom/tools/SqlLineageAnalyzer.java`：用 JSqlParser 分析单个只读查询的字段依赖；不支持的语法明确拒绝。

**提交的 SQL 只被解析，不调用 JDBC 执行，不自动变成 Agent 的执行工具。** SQL 通过预检也不代表获准任意执行。

发布后的读取链使用现有文件：

- `ecom-agent-infrastructure/src/main/java/com/ecom/infrastructure/JdbcKnowledge.java`：查询专家调用口径/上下文检索时，读取已发布且 `active=true` 的知识。
- `ecom-agent-infrastructure/src/main/java/com/ecom/infrastructure/JdbcSemanticWorkbench.java`：语义工作台检索相同的有效知识。

草稿表不参与这些检索。旧版本停用后也不再召回。知识仍按已有指标过滤和关键词规则排序；**这不是向量 RAG，也没有接通 LightRAG。**

知识库保存完整正文；送入 Agent 的证据副本有字符预算：规则召回最多 8000 字符，综合上下文最多 14000 字符，单条正文最多 1200 字符。超过时会标注截断，避免用户发布多篇长文后撑爆模型上下文。这个预算是本地字符边界，不等于真实供应商 token 计费。

## 5. 数据库分别保存什么

迁移文件：

`ecom-agent-infrastructure/src/main/resources/db/migration/V6__knowledge_publishing.sql`

- `knowledge_draft`：草稿内容、所有者、审批状态、乐观锁版本、内容修订号、上一版知识 ID、发布后的知识 ID、SQL 预检结果。
- `knowledge_document`：已发布的知识；新增 `active` 字段控制是否进入检索。原有种子知识默认有效。
- `knowledge_publishing_audit`：创建、编辑、创建修订版、发布、拒绝的动作及内容快照。审核备注随发布/拒绝动作保存。

发布正文、血缘 JSON 和审计快照使用 `MEDIUMTEXT`，避免中文正文和 SQL 拼接后超出 MySQL 普通 `TEXT` 的字节容量。迁移扩容保留已有知识，不改写原正文。

注意两种版本不同：

- `version`：同一草稿的操作版本。创建为 1，每次编辑或审核增加 1，用来处理并发。
- `revision`：知识内容的修订序号。第一版为 1，从已发布版本创建新草稿后为 2。

## 6. API 契约

基础路径：`/api/knowledge/drafts`。

- `GET /`：当前用户最近 100 份草稿/审核结果。
- `POST /`：创建草稿。
- `GET /{id}`：读取本人草稿。
- `PUT /{id}`：编辑草稿。
- `POST /{id}/publish`：人工确认发布。
- `POST /{id}/reject`：人工确认拒绝。
- `POST /{id}/revisions`：从本人仍有效的已发布版本创建新草稿。
- `GET /{id}/audit`：读取本人的动作记录。

创建示例：

```json
{
  "layer": "L3_RULE",
  "metric": "GMV",
  "title": "支付时间口径",
  "content": "GMV 按支付日期统计，不按订单创建日期统计。",
  "sql": ""
}
```

编辑示例：`expectedVersion` 必须使用刚读取的实际版本，而不是一直写 1。

```json
{
  "expectedVersion": 1,
  "content": {
    "layer": "L3_RULE",
    "metric": "GMV",
    "title": "支付时间口径",
    "content": "GMV 按支付日期统计；只统计 PAID 订单，不等于退款后的净收入。",
    "sql": ""
  }
}
```

发布/拒绝示例：

```json
{
  "expectedVersion": 2,
  "confirmed": true,
  "note": "已核对本地指标定义与支付订单筛选条件，确认口径一致。"
}
```

创建修订版只需 `{"expectedVersion":3}`，其中 3 同样是示例，应使用当前返回值。

他人或不存在的草稿均返回 `404 / KNOWLEDGE_NOT_FOUND`，不泄露是否存在。旧版本冲突、重复审核、修订竞争返回 `409`。格式或 SQL 边界不通过返回 `400`。

## 7. 本地人工确认不等于企业双人审批

当前登录用户可以确认自己的草稿，这是个人学习环境的显式人工审核。

**草稿和审核记录按所有者隔离；发布后的知识会进入本地系统共享知识库，其他 `ANALYST` 也可能召回。** 不要发布个人信息、密钥或无权共享的商业资料。

本批没有实现以下企业治理能力：

- 独立发布者/审批者角色、禁止自己审核自己。
- 审批人分配、多级会签、审批通知。
- 多租户隔离与发布知识访问控制。
- 自动判断业务口径是否真实正确、自动消除不同知识之间的冲突。
- 审计防篡改存储、合规保留策略。
- TisPlus、DataWorks 等平台采集与发布回写。

`L1_MODEL` 文档只是模型说明，不会自动改变数据库 Schema；`L4_LINEAGE` 文档也不会修改实际血缘分析器。这些限制应该在验收表中继续保留。

## 8. 自动化验收

测试文件：

`ecom-agent-bootstrap/src/test/java/com/ecom/KnowledgePublishingTest.java`

已编写 15 项测试，覆盖：

1. 草稿不召回，显式发布后进入查询专家和工作台证据。
2. 读取、编辑、发布、拒绝、修订、审计全部检查所有者。
3. 登录、角色、CSRF 和越权 404。
4. 陈旧版本不能覆盖内容，也不能批准已变更的草稿。
5. 已发布内容不可直接编辑或重复发布。
6. 不勾选确认、不写审核备注，不允许审核。
7. 拒绝的知识不进入召回。
8. 未注册指标、未知层级、超长或空正文、明显误粘密钥被拒绝。
9. 四种知识层和通用指标 `*`；SQL 预检不执行、不产生查询审计。
10. 写 SQL、越权字段、未知表、多语句无法保存。
11. 发布时重新检查当前指标注册状态。
12. 新版本发布保留历史，只召回有效版本。
13. HTTP 并发版本冲突返回 409，确认默认不是 true。
14. 两个真实连接竞争发布修订版：只有一个成功，失败者完整回滚。
15. 多篇长文发布后，Agent 上下文保持字符预算，知识库原文仍完整保存。

2026-10-01 的统一 `Maven verify` 已通过：bootstrap 256 项、eval 22 项，共 278 项 Java 测试，0 失败、0 跳过；其中 `KnowledgePublishingTest` 15 项通过。网页隔离库已验证草稿创建、发布、审核记录及查询专家可召回；真实百炼与生产环境仍需单独验收。

## 9. 建议学习顺序

先看 `Content` 和 `Review` 的字段，再看 Controller 怎样接收请求；接着学习 `JdbcTemplate` 的带参数查询、`WHERE owner=?` 的隔离、`version` 的乐观锁，最后理解 `@Transactional` 为什么能防止“草稿显示发布了，但知识表没有内容”。

能够自己解释下面三个问题，就真正理解了这条闭环：

1. 为什么草稿不能直接放进 `knowledge_document`？
2. 如果我打开两个浏览器页面，为什么旧页面不能覆盖新页面？
3. 为什么 SQL 检查通过后，仍然不能让它任意执行？
