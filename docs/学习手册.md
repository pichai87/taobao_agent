# 学习手册：在同一个项目里逐步掌握企业开发

## 你的起点

已经学习 HTML 表单、CSS、DOM、Servlet、对象引用、链表和 PriorityQueue。
现在最重要的不是同时学会所有中间件，而是看清“一次请求怎么经过 Java 代码”。

学习顺序不等于项目重做顺序：下面始终使用同一个仓库。

## 先在网页中验证一次

先读 [网页验证与学习指南](网页验证与学习指南.md)，登录后用默认示例分析。
看到 2600 / 3000 / -400，再展开执行轨迹和 SQL。
不要求你先会看终端 JSON；后续每读懂一层代码，就回到这次请求对应的步骤。

你已学的 `form` 在 index.html 中收集问题；`app.js` 的 submit 监听提交，
`fetch`（发送网络请求）把 JSON 交给 Controller；
`textContent`（元素内的文本内容）把结果显示在页面中，不将返回值当 HTML 执行。

源码入口：`ecom-agent-bootstrap/src/main/resources/static/`。
优先看 app.js 中的表单提交、pollRun、renderReport，其他容错逻辑可以后续学习。

## 第 1 课：Controller 是你学过的 Servlet 的下一步

打开 ecom-agent-api 中 RunController.java。

`@PostMapping("/runs")`：把 POST 请求交给这个方法。
类上的 `@RequestMapping("/api")` 与它组合为 /api/runs。

`@RequestBody Request request`：把 JSON 转成 Java 对象。
`Principal user`：经过认证的当前用户，不是前端随便传的 userId。
`runs.submit(...)`：调用应用服务；Controller 不负责算 GMV 或拼 SQL。

练习：在 submit 上打断点，运行 smoke.ps1，看 question、date 和 user.getName()。

## 第 2 课：对象引用仍是同一个概念

打开 domain/Analysis.java，先看 Request、Run、Daily 三个 record。

record（记录类）：适合表示一组数据，自动提供构造方法和访问方法。
`run.id()` 获取任务编号；与普通类的 getId() 作用类似。

`List<Daily>` 是装有 Daily 对象引用的集合。
遍历 `for (Daily row : rows)` 每次拿到一条记录，不是自动遍历它的所有字段。

对照你之前的链表疑问：保存一个对象引用不等于复制整个对象；
`p = p.next` 是换了引用，`p.next = node` 是改了对象里的连接关系。

练习：在 AttributionCalculator 中观察 rows；说出 list.size() 与 row.orders() 的区别。

## 第 3 课：接口、实现类和依赖注入

打开 Ports.java，再打开 JdbcAnalyticsReader.java。

interface（接口）：声明“需要什么能力”。
implements（实现）：提供具体做法。
依赖注入：Spring 帮你把实现对象传进构造方法。

AnalysisWorkflow 依赖 AnalyticsReader 接口，而不是直接依赖某个数据库厂商。
将来接真正数仓时，不需要把 Controller 和归因公式重写。

练习：找到 AnalyticsReader 是在哪里 new 出来的，以及两个 JdbcTemplate 分别连接什么。

## 第 4 课：SQL、MyBatis 与 JDBC

先读 V1__schema.sql，再看 MetricMapper 与 JdbcAnalyticsReader。

MyBatis：把接口方法映射为 SQL；这里查询指标字典。
JdbcTemplate：简化 JDBC 的连接、执行、结果映射；这里执行审核模板。
PreparedStatement（预编译语句）：SQL 结构与参数分开传递，避免把值拼成指令。
Flyway（数据库迁移）：记录哪些版本的建表脚本已经执行。

练习：解释 WHERE stat_date = ? 中的 ?。
然后运行测试，确认未审核的 SELECT 也会被拒绝。

## 第 5 课：真正的 Agent 编排在哪

打开 AnalysisWorkflow.java，从 execute 开始读：

plan 规划 → semantic 口径 → query 查询 → calculate 计算 → critic 校验 → report 报告。

StateGraph（状态图）：描述节点和执行关系，框架负责调度。
Skill（技能）：已审核任务说明和工具清单；不是给类换个名字就变成“多智能体”。
本批是受控图工作流，不是自由反复行动的 ReAct Agent，也未完成动态 Supervisor。

LLM_CLASSIFIER 模式使用模型选意图，输出必须是枚举值；
OFFLINE_RULES 用关键词选意图，便于没有密钥时调试。
两种模式共用查询、计算、安全和持久化代码。

练习：对比“GMV 是什么”和“GMV 为什么下降”的节点数据。
前者没有业务 SQL，后者有两次查询。

## 第 6 课：企业代码为什么多出这么多状态

打开 RunService.java 和 JdbcRunStore.java。

幂等（idempotency）：相同用户用相同键提交相同请求，只产生一个任务。
检查点（checkpoint）：保存已完成的步骤和结果，进程重启后可继续。
CAS（比较后更新）：只有状态仍符合预期时才更新，避免两个请求同时认领任务。
有界线程池：最多 4 个工作线程、16 个等待任务；满了明确拒绝，而非无限占内存。

练习：把 reviewRequired 改成 true，确认审批前没有 tool_call_audit。
再取消任务，解释为什么审批接口会拒绝。

## 第 7 课：测试不等于“运行没报错”

读 AnalysisIntegrationTest，然后读 SafetyAndCalculationTest。
assert（断言）：把预期结果写成可以自动检查的条件。
单元测试：单独检查公式/规则。集成测试：同时检查框架、数据库和接口。

练习：故意把某个预期 GMV 改错，观察测试如何失败，然后恢复你的修改。
再补一条自己想到的边界测试：对比日没有数据。

## 学习记录建议

每次只记录四件事：看了哪个文件、能解释哪段代码、哪里还不懂、做了什么验证。
下一次提问可以直接发“文件名 + 方法名 + 疑问”。后续学习总结继续补在 docs，
不靠聊天记忆作为唯一文档。
