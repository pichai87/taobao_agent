# 数据与指标

## 本机数据够不够

本批主链够用：90 天（2026-06-17 至 2026-09-14）、3 个品类、
2696 笔订单、270 条品类每日流量。全为合成数据，没有爬取或使用真实个人信息。

为了完成最终企业功能仍需补数据：
退款/取消流水、渠道投放、商品成本、库存、去重访客明细、
运营活动记录、指标字典与审核过的业务文档。
没有这些数据时，不能解释广告效果、利润下降或证明活动导致成交变化。

MySQL 配置默认只建表，不自动装入合成数据。
需要在独立的学习数据库中显式加载 db/local/V2__synthetic_seed.sql，
不能把学习数据混到真实业务库。

## 可复现实验

2026-09-11：三品类各 10 单，每单 100 元，GMV 3000 元。
2026-09-12：家电降为 6 单，另外两类各 10 单，GMV 2600 元。

差额 -400 元，变化率 -400 / 3000 ≈ -13.3333%。
家电贡献 -400 元，其余两类 0 元。
只能说家电品类解释了这次金额差额，不能说“广告投放失败是原因”。

## 指标释义

- GMV（Gross Merchandise Value）：这里按已支付订单金额统计，不扣退款。
- ORDERS：已支付订单笔数。
- UV（Unique Visitors）：独立访客数；合成数据假定不同品类客群互斥。
- CVR（Conversion Rate）：本口径是订单数 / UV，不是支付买家数 / UV，真实多单场景可能超过 100%。
- AOV（Average Order Value）：客单价，这里为 GMV / 支付订单数。

除数为零返回 null，表示不可计算，不返回假造的 0%。
金钱使用 BigDecimal，不使用二进制浮点数累加。

## 读模型限制

analytics_daily 从 traffic_daily 出发 LEFT JOIN 支付订单聚合。
因此只有订单、没有对应流量记录的日期/品类不会进入视图。
真实数据接入前必须做覆盖性检查，不能默默忽略缺失流量的订单。
真实跨品类访客还需要先去重，不得直接沿用本地 UV 加总假设。

知识检索当前返回 4 条审核规则，属于 SQL 口径查询；
没有 Embedding、向量召回、重排或文档入库流水线，不称为已完成 RAG。
