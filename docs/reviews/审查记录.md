# 独立审查与调试记录

更新：2026-09-23。审查对象是本仓库当前实现；不把《技术升级方案》的扩展项纳入本批必需功能。

## 审查原则

- 可复现的数据、权限与状态错误优先于代码风格。
- 各 Agent 使用不同上下文或名称，不自动等于业务能力正确；必须检查数据、工具权限和实际输出。
- 测试使用独立 H2 内存库、合成数据与模拟模型，不读取网页临时 Key，不调用付费模型。
- 本文区分“发现”“已修改”“已测试”，没有运行过的验收不标记通过。

## R-01：缺失流量行导致已支付 GMV 被静默漏掉

优先级：高。状态：代码已修复，H2 迁移行为与 Java 回归已通过。

- 编号：R-01。
- 现象：支付订单存在，但分析报告漏算部分 GMV。
- 根因：流量表作为唯一查询粒度来源，缺少流量行的订单在 JOIN 前已被排除。
- 影响：总额、同比/环比和品类贡献可能同时错误；内部贡献加和仍可能通过，不能靠金额守恒识别。
- 修复文件：`V4__complete_analytics_grain.sql`、`JdbcAnalyticsReader.java`。
- 验证结果：下述独立 H2 迁移前后实验通过，`AnalyticsReadIntegrityTest` 6 项全部通过。
- 未解决限制：未补齐真实流量；目前缺流量时整个多指标读取明确失败。

旧实现 `V1__schema.sql` 的 `analytics_daily` 从 `traffic_daily` 出发 LEFT JOIN 订单聚合。某日期/品类有已支付订单，但没有流量行时，订单金额根本不进入视图。此时查询、计算与贡献加和都可能通过，报告仍是错误金额。

独立内存库复现：

- 品类 present：订单 100 元、存在 UV=10 的流量行。
- 品类 missing_traffic：订单 200 元、没有流量行。
- 基础订单支付额合计 300 元；旧视图返回 100 元。

修复：新增 `V4__complete_analytics_grain.sql`，用“流量粒度 UNION 已支付订单粒度”构建视图键集，再连接两侧数据。缺失流量时保留真实订单金额，UV 保持 NULL，不伪造为 0。`JdbcAnalyticsReader` 遇到未知 UV 抛出 `DATA_COVERAGE_INCOMPLETE`，阻止生成看似完整的多指标报告。

迁移实测结果：同一组数据，应用 V4 前 GMV=100.00，应用后 GMV=300.00；缺流量品类 UV=NULL，已知流量品类 UV=10。

边界：这不是业务数据修复。需要补齐流量来源；将来若允许只查 GMV 时继续返回结果，应先让契约显式表达某些指标不可用，不能把 `Daily.uv` 的 Java 基本类型默认值 0 当作实测流量。

## R-02：LIMIT 500 会将部分结果冒充完整结果

优先级：高。状态：代码已修复，SQL 边界行为与 Java 回归已通过。

- 编号：R-02。
- 现象：超过 500 行时返回错误总额但任务表现为成功。
- 根因：SQL 和 JDBC 同时截断，调用方看不到第 501 行，无法区分完整结果与被截断结果。
- 影响：数据量或维度增大后无告警漏算，趋势明细也可能不完整。
- 修复文件：`ApprovedSql.java`、`JdbcAnalyticsReader.java`。
- 验证结果：独立 H2 中完整 501.00、旧查询 500.00、新哨兵 501 行；Java 目标日与趋势拒绝路径均已通过测试。
- 未解决限制：查询仍有 500 行业务上限，需要用户缩小范围；未实现分页或大结果流式计算。

旧 `ApprovedSql` 使用 `LIMIT 500`，`JdbcAnalyticsReader` 又设置 `setMaxRows(500)`。结果超过 500 行时，代码仍正常汇总、写成功审计，无法知道数据库实际有更多数据。

独立内存库复现：同一天 501 个品类，每品类一笔 1 元支付订单和 UV=1。完整 GMV=501.00；旧模板返回 500 行，总额=500.00。

修复：业务行数上限仍为 500，但 SQL/JDBC 最多读取 501 行。第 501 行作为“超限哨兵”；出现时抛出 `QUERY_RESULT_LIMIT_EXCEEDED` 并写失败审计，不返回被截断的金额。目标日查询和趋势查询使用相同防线。

SQL 实测结果：旧模板汇总=500.00；完整汇总=501.00；新读取上限可观察到第 501 行。

## R-03：知识召回忽略问题和指标

优先级：中。状态：主实现已加入按指标/知识层过滤、数量限制及术语相关性排序；工作台集成回归通过。

- 编号：R-03。
- 现象：不同问题和指标获得同样的全部知识文档。
- 复现：调用 `recall("GMV", "GMV")` 与 `recall("CVR", "CVR")`，旧 SQL 不使用任一参数。
- 根因：`JdbcKnowledge.recall` 使用无过滤的全表 SELECT。
- 影响：扩充文档后无关口径混入模型上下文，无法验证引用资料对应所问指标。
- 修复文件：主实现 Agent 正在改造 `JdbcKnowledge` 与语义/知识元数据。
- 验证结果：静态代码路径确认；修复后需覆盖不同指标、来源和数量限制。
- 未解决限制：旧实现尚无版本有效期过滤；不能据此声称已完成完整文档 RAG。

`JdbcKnowledge.recall(question, metric)` 旧实现无条件执行 `SELECT ... FROM knowledge_document ORDER BY id`，两个参数都不参与查询。4 条固定规则时能够提供解释材料，但增添多指标、活动文档后会把无关资料全量返回，也没有版本、生效日期或权限筛选。

最小建议：将受控指标口径和一般知识分开；指标必须经过注册表匹配，知识查询需要匹配条件和条数限制。来源、版本、命中理由应进入结果。不能把“全表返回”改名为检索系统就标记完成。

## R-04：语义聚合可能把跨日 UV 累加冒充去重人数

优先级：高。状态：主实现已拒绝跨日消去日期维度的 UV 聚合，反例测试通过。

- 编号：R-04。
- 现象：查询多日 UV/CVR，维度未包含 `stat_date`，编译器仍生成 `SUM(uv)`。
- 复现：`Query([UV], [category], 2030-01-01, 2030-01-02, null, 10)`；自定义指标 `SUM(gmv)/SUM(uv)` 同样存在此问题。
- 根因：定义层只知道 SUM/RATIO，未校验 UV 在时间维度上的不可加性。
- 影响：跨日访问次数可能误标独立访客数，相关比值也没有原口径保障。
- 修复文件：建议在 `SemanticSqlCompiler` 依据指标使用的物理度量和分组维度增加限制，禁止跨日消去日期的 UV 聚合；GMV/订单/AOV 的合法跨日汇总保留。
- 验证结果：`SemanticBoundaryTest` 的 UV、CVR、自定义比值三类反例与合法逐日查询对照已通过。
- 未解决限制：当前没有跨日访客明细，不能计算真实区间去重 UV。

## R-05：自定义指标代码与维度输出名称冲突

优先级：中。状态：主实现已拒绝维度保留名，并为指标 SQL 别名添加安全引用；反例测试通过。

- 编号：R-05。
- 现象：指标注册代码 `CATEGORY` 或 `STAT_DATE` 通过格式检查，产生与维度同名的 SQL 输出列。
- 复现：注册 `MetricDef("CATEGORY", ..., SUM, "gmv", ...)`，再选择 category 维度。
- 根因：只验证代码是字母数字下划线，没有保留维度字段名。
- 影响：JDBC/JSON 按列名映射时可能覆盖维度标签，血缘输出也会歧义。
- 修复文件：建议 `SemanticSqlCompiler.validateDefinition` 禁止保留名称，或为指标输出统一不冲突的安全别名。
- 验证结果：`SemanticBoundaryTest` 的两个保留名反例已通过。
- 未解决限制：仅支持当前单事实模型的注册字段；不能任意声明 SQL 表达式。安全引用策略仍待集成回归。

## R-06：SQL SUM 会吞掉缺失流量，绕过明细空值检查

优先级：高。状态：主实现已加入聚合空值传播，自动回归通过。

- 编号：R-06。
- 现象：一个品类 UV=NULL、另一个 UV=10，`SUM(uv)` 得到 10，已不再是 NULL。
- 复现：在 V4 完整视图中对缺流量与有流量的品类不分组汇总，再检查 `wasNull()`。
- 根因：空值检查在 SQL 聚合后执行，而 SQL SUM 默认忽略 NULL。
- 影响：原 R-01 的明细拒绝防线在新聚合执行路径中被绕过，CVR 分母不完整但看似有效。
- 修复文件：`SemanticSqlCompiler.aggregate` 使用 `CASE WHEN COUNT(uv)=COUNT(*) THEN SUM(uv) ELSE NULL END`；缺失任一流量时 UV/CVR 保持未知，GMV 等完整指标仍可计算。明细 Agent 链继续明确失败，不伪造 UV。
- 验证结果：旧 SQL 独立 H2 实验实际得到 orders=2、partial_uv=10、CVR=0.2，同时 missing_uv_rows=1。修复后编译 SQL 的 H2 执行测试验证 UV/CVR 均为 NULL，而完整 GMV=300.00；相关用例已通过。
- 未解决限制：返回 NULL 需要页面正确标为不可计算，不能渲染成 0；目前尚未完成网页联调。

## R-07：Top N 请求只排序但没有执行数量限制

优先级：中。状态：独立解析器和三条工作流均已接入，基础回归与新增词边界反例通过。

- 编号：R-07。
- 现象：用户问 GMV Top 1，原三条执行链仍返回三个品类。
- 复现：原 `AnalysisWorkflow` / `ToolCallingWorkflow` / `AnalysisAgent` 中 TOP_N 都只执行排序，不读取 N。
- 根因：意图只有 TOP_N 枚举，没有从原问题提取数量并约束输出。
- 影响：实际结果不满足明确的问题要求，普通“排序正确”测试无法发现。
- 修复文件：新增 `QuestionConstraints`，提供 `topN` 与 `limit`；`RulePlanner` 识别“前五名”等表达；三条工作流需要调用统一裁剪。knowledge 模块为复用解析增加 tools 依赖，无循环。
- 验证结果：`QuestionConstraintsTest` 全部 39 项通过，包含阿拉伯数字 1..100、中文一..十、未指定数量、非法值和冲突值。回归曾暴露测试夹具字符串 TOP_N 被误当自然语言 Top N；补词边界后，TOP_N/desktop/stopping/laptop/metadata_top_count 5 个反例均通过。
- 未解决限制：中文十一及以上、模糊“前几名”等拒绝并要求明确数量，不擅自猜测；问题包含多个不同 N 时也拒绝。

## R-08：显式非 GMV 问题可能被默默当成 GMV 回答

优先级：高。状态：入口已加入约束，自动回归通过。

- 编号：R-08。
- 现象：表单 metric=GMV，文本问“订单数量多少”，原规则会匹配 QUERY，最终主报告仍给金额。
- 复现：旧 `RulePlanner` 将含“订单”的文本识别 QUERY，`RunService` 只检查表单指标为 GMV，不检查文本表达的其他指标。
- 根因：文本约束和执行链能力不一致，未明确拒绝无法完成的用户问题。
- 影响：用户得到不相干结果，模型解释可能造成“多指标已经完整支持”的误解。
- 修复文件：`QuestionConstraints.validate` 与 `RunService.submit`，识别明确的 UV/CVR/AOV/订单数量及常见未支持指标，返回 `QUESTION_METRIC_NOT_SUPPORTED`；保留合法“GMV 按支付订单金额统计”问题。
- 验证结果：`QuestionConstraintsTest` 的非 GMV 问题反例和 GMV/状态问题正例已通过。
- 未解决限制：这是主 Agent 分析链的保守能力边界，不是通用自然语言解析。新语义工作台可以按结构化计划查询多个已注册指标，但不能因此宣称主分析链的全部多指标自然语言问答已完成。

## R-09：终态 SSE 和页面轮询没有排空事件分页

优先级：中。状态：主实现修复完成，真实 MVC + SSE 回放回归通过。

- 编号：R-09。
- 现象：任务已有 1001 条持久事件，SSE 只交付前 1000 条就发送终态并关闭；页面终态轮询也只取一页。
- 复现：`RunStore.events` 的 SQL 带 `LIMIT 1000`；创建 1001 条合成事件并订阅终态任务可触发。
- 根因：订阅端把“读了一页”当成“所有持久事件均已读完”。
- 影响：最后交接、错误或报告事件丢失，前端状态与完整轨迹不一致。
- 修复文件：`EventStreamController` 满页时继续下次读取，不提前推送终态；`app.js` 轮询通过游标循环取完分页再渲染。
- 验证结果：`WebProtocolReviewTest` 真实经过认证 MVC、H2 与异步 `SseEmitter`，1001 条按序无重复交付、终态位于末尾；after 续接与 Last-Event-ID 优先级用例也已通过。
- 未解决限制：本次不是网络代理、慢消费者或大规模连接压力测试；超时后需要保留游标重新订阅。

## R-10：任务终态先于最终事件提交，订阅存在竞态

优先级：中。状态：主实现已采用数据库事务，状态原子性和回滚新增测试通过。

- 编号：R-10。
- 现象：失败或取消时，订阅可能先看到 FAILED/CANCELLED，读取事件时 STOPPED/CANCELLED 事件尚未入库，随后关闭连接。
- 复现：旧 `RunService` 依次调用状态更新和 `event`，两者是独立数据库操作，存在确定的提交间隙；单纯先读取状态再读取事件无法消除此间隙。
- 根因：终态与对应最终事件没有在同一事务提交。
- 影响：客户端收到终态但缺少最终说明；若无条件补写失败事件，取消后晚到的 worker 异常又会制造假的 STOPPED 事件。
- 修复文件：`JdbcRunStore.failWithEvent/cancelWithEvent` 使用事务，将条件更新与事件插入一起提交；`RunService` 失败、队列拒绝及取消入口使用新操作。CAS 失败不写事件。
- 验证结果：重复失败、取消 CAS 失效、晚到 worker 错误三类断言已通过。还用仅作用于唯一测试任务的 H2 临时 CHECK 强制事件写入失败，验证失败和取消的状态更新一起回滚；新增 4 项均通过，`WebProtocolReviewTest` 总计 11 项通过。
- 未解决限制：只保证本地关系库中的任务状态与事件原子性，不宣称外部消息或多实例 exactly-once。

## R-11：将一个网络块误当成一个 SSE 事件判断大小

优先级：中。状态：主实现修复完成，Node 反例通过。

- 编号：R-11。
- 现象：代理或浏览器一次交付许多正常小事件，合并数据超过 131072 字符时被误报 STREAM_EVENT_TOO_LARGE。
- 复现：一次向 parser 推入 1000 个正常小帧的合并网络块，总长度大于限制，但每个事件远小于限制。
- 根因：解析前判断整个接收 buffer 的大小，没有区分网络分块与 SSE 事件边界。
- 影响：合法长轨迹触发无意义的断线/重连，阻碍事件正常消费。
- 修复文件：`stream.js` 逐帧解析并检查单帧大小，处理完成帧后再限制剩余未完成 buffer。
- 验证结果：`scripts/stream.review.test.cjs` 验证合并 1000 小帧正常通过，超限的单个完整帧仍拒绝；实际 Node 运行通过。
- 未解决限制：字符数限制不是精确网络字节上限；本批没有将其宣称为内存压力测试。

## R-12：SSE 消费者异常后释放 reader 锁但未取消网络流

优先级：中。状态：主实现修复完成，Node 网络流回归通过。

- 编号：R-12。
- 现象：解析/回调异常退出消费时只调用 releaseLock，底层请求可能继续存在到服务端超时。
- 复现：真实 Node ReadableStream 保持打开，onEvent 抛异常；旧 finally 不触发流的 cancel 回调。
- 根因：释放读取锁与取消读取是不同操作，前者不会关闭传输。
- 影响：自动重连期间旧连接可能继续占用有限的服务端 SSE 席位。
- 修复文件：`stream.js` finally 先取消 reader（容忍已关闭异常），再释放锁。
- 验证结果：`scripts/stream.review.test.cjs` 证明消费者异常会调用底层 cancel，并确认认证头不进入 URL；实际 Node 运行 3/3 通过。
- 未解决限制：此验证使用 Node 标准流，真实浏览器/代理断线和慢客户端压力仍需另行验收。
