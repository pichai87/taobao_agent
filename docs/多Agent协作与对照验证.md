# 多 Agent 协作与对照验证

更新：2026-09-14。本文记录实际代码，而不是下一阶段设想。多 Agent 协作已实现，但真实百炼多 Agent 端到端与生产验收尚未完成。

## 1. 与原文的对应关系

依据用户给出的[淘宝原文](https://mp.weixin.qq.com/s/BpsscOnYq-DWsb_DrID8hA)及[注明原文来源的转载](https://www.aixq.cc/67378.html)。上一批已通过浏览器读取原文架构章节；本轮微信直读失败，重新核对转载的意图识别、Supervisor、Query/Analysis/Ops/Other 分工与上下文隔离思路。这里没有获得淘宝内部源码或数据。

沿用“识别目标 → 调度专家 → 专家使用受限工具 → 校验交付”的结构；不把原文全部工程能力标为完成。

- IntentAgent（意图智能体）：模型输出目标、置信度；低置信度或可恢复的响应格式问题使用明确标记的规则回退。认证、供应商错误不伪装成离线成功。日期仍由表单指定；未实现任意自然语言日期、多意图拆解。
- Supervisor（主管/调度器）：Java 规则决定专家路线、检查交接范围。它不是额外的一次自由模型对话，也不计入模型请求数。
- QueryAgent（查询专家）：独立提示词、对话和查询工具；负责口径证据、受控 SQL 查询、返回证据包。
- AnalysisAgent（分析专家）：独立提示词和对话，只有数据请求与当前目标的计算工具；不能直接查库。
- OpsAgent（运维专家）：只读当前账号最近任务的状态元数据，不具备重启、删库或修改其他用户任务的权限。
- OtherAgent（其他问题专家）：说明本项目的能力边界，不假装能回答所有问题。

多个专家可以使用同一个百炼模型。区别在于各自的职责、上下文、工具权限和交接协议，不要求购买多个模型。

## 2. 实际调用链：为什么 GMV 下降

1. IntentAgent 输出 COMPARE 或 ATTRIBUTION（对比/贡献分析）。
2. Supervisor 将目标、日期交给 AnalysisAgent。
3. AnalysisAgent 调用 request_data，请求两期数据；这不是自己执行 SQL。
4. Supervisor 校验范围并派发 QueryAgent。
5. QueryAgent 独立调用 explain_metric、query_daily，查询两期真实测试库数据。
6. Java 构造 EvidencePacket（证据包）：任务 ID、日期、范围、明细、口径与 SQL 记录。
7. Supervisor 返回证据包。QueryAgent 的整段模型对话不会复制给 AnalysisAgent。
8. AnalysisAgent 调用 compare_gmv，由 Java BigDecimal 计算差额与品类贡献，再生成解释。
9. 校验节点检查目标、证据、计算结果和贡献加和；报告节点保存最终报告。

简单查数只调用 QueryAgent；定义、任务状态、能力说明各走自己的分支。不会为了展示“多”而强制所有专家上场。

目前是按任务按需协作，不是所有专家并发运行，也不是递归归因树。某些错误可在专家循环内修正；越权、错误交接、凭据失效、预算耗尽等会终止任务。

## 3. 如何证明不是只换了名字

- StateGraph 实际执行 intent → supervisor → critic → report。
- 每个专家新建自己的消息列表，并真正调用同一个 Gateway（模型请求接口）。
- 每次模型请求只声明该专家当前允许的工具；执行层再次检查白名单，不仅靠提示词约束。
- AnalysisAgent 没有 AnalyticsReader 数据库读取依赖；取数必须经过 DataDelegate（数据请求接口）。
- 证据包校验任务 ID、目标日期、范围、明细日期与必要证据；不能拿别的任务数据冒充当前结果。
- 网页“协作链”根据实际事件展示参与专家、模型请求数和交接，不预先画一条假成功流程。

## 4. 单/多 Agent 对照实验

原单 Agent ToolCallingWorkflow 保留。AgentComparisonTest 对同一 H2 数据、相同六类目标分别执行两种真实工作流；只将供应商决策替换成可重复的 Fixture（固定测试响应）。完整输出见 [测试原始记录](verification/agent-comparison-20260914.json)。

已测结论：

- 六类用例的结构化结果一致，包括两期 GMV 2600/3000、差额 -400。这里只能说明这些固定用例通过，不是模型准确率达到 100%。
- 单 Agent 每次可见六个工具；多 Agent 每次最多两个。分析专家直接请求 query_daily 会被拒绝；单 Agent 本就拥有该工具。
- 在查询专家内部加入测试干扰文字，分析专家的输入中没有该文字，而保留必要结构化数据。证明本次交接隔离有效，不代表能防住所有提示词注入。
- 对比/贡献/趋势/排序用例：模型请求数由 4 增至 7；简单查询保持 4；定义由 2 增至 3。
- 对比用例累积工具菜单条目由 24 降为 13，但序列化请求字节数约由 15.2 KB 增至 16.2 KB。字节数不是 token，更不是实际账单。
- 缺失对比期数据时，测试会触发再次交接补数；错误日期、跨任务证据、越权工具、错误路由、取消和凭据清除会被拒绝或停止。

重要归因限制：工具动态裁剪、强类型证据包也能用于优秀的单 Agent 实现。因此本实验验证的是“当前两种实现”的边界差异，不能把所有收益归功于 Agent 数量。只有六个工具、简单问题时，多 Agent 未必值得额外延迟；增加不同权限和复杂专家任务后，这种拆分更有工程价值。

## 5. 尚不能下的结论，以及真实 A/B 方法

本轮没有读取用户 Key、没有调用付费模型。不能声称多 Agent 更准确、更便宜、更快。此前用户展示的是单 Agent 真实轨迹，不作为多 Agent 联调证据。

真实 A/B（同条件对照）需在用户同意费用后进行：固定同一模型版本、日期、数据和问题集，两种模式各重复至少三次；记录成功率、金额/证据正确性、越权拒绝、遗漏数据修复、供应商报告 token、总耗时与调用次数。三次仅作小样本试验，不足以证明普遍优势。比较时保留失败，不挑选最好的一次。

若要区分“拓扑收益”和“工具裁剪收益”，应进一步增加一个具有动态工具白名单、证据门槛的优化单 Agent 组，而不是只比较当前六工具基线。

## 6. 安全与预算

多 Agent 全局共享：16 次模型请求、24 次工具请求、6 次派发、30000 个供应商报告 token、180 秒操作边界时限。单次 HTTP 仍有 25 秒超时；不是强制在第 180 秒中断正在执行的网络请求。局部循环最多 Query 6 轮、Analysis 7 轮、Ops/Other 3 轮，并仍受全局上限约束。

同一用户单/多 Agent 共用执行锁。取消、临时配置过期或清除后，在下一个检查点停止。模型任务暂不支持断点恢复，需重新提交；离线恢复能力仍保留。日志不保存 Key 或完整专家对话。自然语言解释仍需人工核对，不能代替 Java 金额。

## 7. 网页使用与接口

登录 → 保存百炼临时配置 → 执行方式选择“多 Agent 专家协作” → 建议勾选执行前确认 → 开始分析 → 确认执行。保存配置后默认选择多 Agent，但保存本身不会调用模型。

单 Agent 对照模式仍可选择。任务页面显示真实角色和交接；历史单 Agent 任务不会被改造成多 Agent。服务重启后临时 Key 不保留，需要重新填写。

POST /api/runs 新增 executionMode：LLM_MULTI_AGENT 或 LLM_TOOL_CALLING；两者都必须带有效的 modelSessionId。旧请求有会话引用但没传 executionMode 时仍按单 Agent 执行；没有会话引用时沿用默认规划模式。

需求表目录的 Supervisor 行已更新代码基线；用户自己保存的勾选/备注不被自动覆盖。可依据本轮测试补充自己的验收记录，真实模型验收仍应单独完成。

## 8. Java 学习顺序

1. AgentContracts.java：record（记录类）怎样承载目标和证据；对象引用不是整段聊天记录。
2. Supervisor.java：switch 如何按目标分支；DataDelegate 接口如何约束调用方向。
3. QueryAgent.java：List、循环、工具参数校验，以及 DAO 查询怎样变成证据包。
4. AnalysisAgent.java：通过接口请求数据，再调用 Java 计算器；不要让模型算金额。
5. AgentRuntime.java：共享预算、独立消息列表、事件记录和异常终止。
6. MultiAgentWorkflow.java：StateGraph 把意图、调度、校验、保存串起来。
7. AgentComparisonTest 与 MultiAgentIntegrationTest：断言如何证明结果和权限边界，而不是只看到页面没有报错。
